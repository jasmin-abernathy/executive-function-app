The garden rule

A feature does not belong here simply because it is possible. It has to answer a real use case.

Approach

Start with the problem, not the feature list.

The projects shown here are not trying to become sprawling platforms. The aim is to test focused answers, document their limits, and keep the technology understandable.

01

Useful first

Each project starts from an observed need, a concrete friction point, or a poorly served use case. The feature comes afterwards.

02

Local when it makes sense

On-device processing and fewer remote exchanges are preferred whenever they genuinely improve the product.

03

Open and verifiable

Source code, documentation and limitations should be inspectable. Open source is a way to make the tool more controllable and durable.

04

Restrained by design

No “just in case” collection, no decorative dependencies, and no features added merely to fill a marketing page.
